# Правила разработки Unreal Engine

Применять только перечисленные правила. Текущая редакция утверждена пользователем, включая делегированное завершение критических разделов. Дальнейшие изменения требуют нового явного указания пользователя.

## Базовый стандарт C++

- **CODE-001** — Следовать [Epic C++ Coding Standard](https://dev.epicgames.com/documentation/unreal-engine/epic-cplusplus-coding-standard-for-unreal-engine) во всём C++-коде. При конфликте отдавать приоритет отдельно утверждённым правилам проекта.
- **CODE-002** — Соблюдать [Include What You Use](https://dev.epicgames.com/documentation/unreal-engine/include-what-you-use-iwyu-for-unreal-engine-programming): каждый header включает собственные зависимости, `.cpp` первым включает соответствующий `.h`, монолитные `Engine.h` и `UnrealEd.h` не используются.

## Правила для coding-агента

- **AGENT-001** — Перед использованием Unreal API проверять его наличие, сигнатуру, header и module в зафиксированной версии Engine. Не писать API по памяти и не переносить пример из другой версии без проверки.
- **AGENT-002** — Не добиваться успешной сборки удалением или отключением тестов, `check`, `ensure`, валидации или обработки ошибок. Исправлять первопричину. Изменять тест или контракт только после отдельного согласования.
- **AGENT-003** — Сообщать, что сборка или тесты прошли, только если точная команда выполнена после последнего изменения и завершилась успешно. В остальных случаях явно указывать, что проверка не запускалась, либо сообщать причину блокировки.
- **AGENT-004** — Перед изменением проверять текущий код и `git diff`. Изменять только файлы задачи, сохранять пользовательские правки и не переписывать несвязанный код. При конфликте правок останавливаться и запрашивать решение.
- **AGENT-005** — Перед исправлением дефекта сначала воспроизводить его и определять первопричину. После исправления повторять тот же сценарий и запускать регрессионный тест. Не вносить спекулятивные исправления без подтверждённой причины.
- **AGENT-006** — Не редактировать generated-файлы, IDE project files, `Binaries`, `Intermediate`, `Saved` и Derived Data Cache для реализации исправления. Изменять исходники проекта, `Build.cs`, `Target.cs`, config или assets и запускать штатную генерацию. Не изменять Engine или сторонний plugin без отдельного разрешения.
- **AGENT-007** — Перед написанием кода для feature читать этот файл и фиксировать применимые rule ID. После всех изменений проводить независимую проверку финального diff по применимым правилам. Не завершать feature при наличии нарушения.

## Многопоточность

- **MT-001** — Не обращаться к `UObject` вне Game Thread, кроме API Unreal Engine, явно отмеченных как thread-safe. Передавать фоновым задачам только независимые от `UObject` данные.
- **MT-002** — Выносить в Tasks System тяжёлые вычисления и файловый ввод-вывод, если они вызывают остановки Game Thread. Передавать задаче только независимые данные.
- **MT-003** — Не блокировать Game Thread ожиданием фоновой задачи. Возвращать результат через continuation или callback.
- **MT-004** — Делать общие межпоточные данные неизменяемыми либо защищать их явной синхронизацией. Предпочитать копирование данных и передачу сообщений.
- **MT-005** — Не захватывать сырой `UObject*` в асинхронной задаче. Использовать слабую ссылку и повторно проверять её валидность на Game Thread.

## Ссылки на UObject

- **OBJ-001** — Если поле должно удерживать `UObject` от сборки мусора, использовать `UPROPERTY() TObjectPtr<T>`. Не использовать для такого поля сырой `UObject*`.
- **OBJ-002** — Для не владеющей ссылки на `UObject` использовать `TWeakObjectPtr<T>` и проверять `IsValid()` перед обращением.
- **OBJ-003** — Не управлять `UObject` через `TSharedPtr`, `TSharedRef` или `TUniquePtr`. Использовать типы ссылок Unreal Engine для `UObject`.
- **OBJ-004** — Контейнер, который должен удерживать `UObject`, объявлять через `UPROPERTY()` и хранить в нём `TObjectPtr`, например `TArray<TObjectPtr<T>>`.

## Garbage Collection

- **GC-001** — Не создавать и не удалять `UObject` через `new` и `delete`. Использовать `NewObject`, `CreateDefaultSubobject`, `SpawnActor` и `Destroy` по назначению.
- **GC-002** — Вводить pooling для часто создаваемых короткоживущих объектов только после измерений, подтверждающих проблему в `Spawn`/`Destroy` или GC.
- **GC-003** — Не запускать GC вручную во время активного gameplay. Допускать ручной запуск только на экране загрузки и при подтверждённой измерениями необходимости.
- **GC-004** — Не создавать `UObject` только как контейнер данных. Использовать `USTRUCT` или обычную C++-структуру, если не требуются идентичность и жизненный цикл `UObject`.
- **GC-005** — Не изменять настройки GC без измерений на целевых платформах. Сравнивать время кадра, паузы GC и потребление памяти до и после изменения.
- **GC-006** — Не использовать `AddToRoot` как обычный способ управления жизненным циклом. Удерживать объект через `UPROPERTY`, `TStrongObjectPtr` или `FGCObject` по назначению. Допускать `AddToRoot` только для явно глобального объекта с гарантированным `RemoveFromRoot` при shutdown.

## Ресурсы

- **ASSET-001** — Ссылаться на опциональные ресурсы через `TSoftObjectPtr` или `TSoftClassPtr` и загружать их асинхронно до использования.
- **ASSET-002** — Использовать Hard Reference только для ресурса, который всегда необходим вместе с владельцем ссылки.
- **ASSET-003** — Хранить в DataTable и каталогах опциональных ресурсов только Soft References.
- **ASSET-004** — После асинхронной загрузки сохранять ресурс в `UPROPERTY() TObjectPtr<T>`, если он должен оставаться загруженным.
- **ASSET-005** — Не выполнять синхронную загрузку ресурсов во время gameplay. Использовать асинхронную загрузку, чтобы не блокировать Game Thread.
- **ASSET-006** — Проверять новую Hard Reference в долгоживущем объекте через Reference Viewer и Size Map.
- **ASSET-007** — Не собирать пути к ресурсам вручную строками. Использовать Soft References или `FPrimaryAssetId`.
- **ASSET-008** — Управлять динамическим контентом, DLC и крупными каталогами через Asset Manager и `FPrimaryAssetId`, а не через разрозненные Soft References.
- **ASSET-009** — Обрабатывать ошибку, отмену и `null` при асинхронной загрузке. Не использовать ресурс до успешного завершения загрузки.

## Сериализация данных

- **DATA-001** — Не сериализовать и не реплицировать сырую память структуры через `memcpy`, `sizeof` или запись padding. Сериализовать поля явно через Unreal serialization, добавлять версию формата и учитывать различия платформ.
- **DATA-002** — Использовать стабильные значения для сохраняемых и сетевых enum и ID. Не переиспользовать ранее выпущенное числовое значение и не использовать array index или отображаемое имя как постоянный ID. При изменении выполнять миграцию.

## Архитектура C++ и Blueprint

- **ARCH-001** — Приводить тип к конкретному Blueprint-классу только когда допустима жёсткая зависимость от него. В остальных случаях использовать интерфейс или нативный C++-базовый класс.
- **ARCH-002** — Использовать `Level Blueprint` только для уникальной логики конкретного уровня. Размещать переиспользуемую и авторитетную gameplay-логику в C++-классах, компонентах или subsystems.
- **ARCH-003** — Не хранить World-зависимые объекты и состояние в глобальном singleton или `UGameInstanceSubsystem`. Использовать `UWorldSubsystem`. Применять `UGameInstanceSubsystem` только для данных, которые должны переживать смену карты.
- **ARCH-004** — Разрешать `GameClient` и `GameEditor` зависеть от `GameCore`. Не разрешать `GameCore` зависеть от них. Не подключать UI, визуальные эффекты или Editor-код к серверной сборке.

## Внешние зависимости

- **DEP-001** — Подключать новый plugin или стороннюю библиотеку только после отдельного архитектурного согласования и проверки лицензии, фиксированной версии, поддержки целевых платформ и сборок `Editor`, `Client` и `Server`. Изолировать внешний API за проектным adapter и не обновлять зависимость без регрессионных тестов.

## Жизненный цикл Unreal Engine

- **LIFE-001** — В конструкторе `UObject` или Actor только задавать значения по умолчанию и создавать default subobjects. Не обращаться к World, не создавать Actors и не запускать gameplay-логику. Выполнять runtime-инициализацию в `BeginPlay`, `OnRegister` или явном `Initialize`.
- **LIFE-002** — Снимать при завершении жизни всё, что зарегистрировал объект: очищать timers, отписывать delegates по сохранённым handles и отменять async requests в `EndPlay`, `Uninitialize` или `Deinitialize`.
- **LIFE-003** — Не считать другую систему готовой только потому, что начался `BeginPlay` текущего объекта. Запускать зависимую систему только после явного `Initialize` или события `OnReady`.

## Игровое время

- **TIME-001** — Не связывать gameplay-результат с количеством кадров или FPS. Использовать `DeltaSeconds`, server timestamps либо фиксированный simulation step по назначению и проверять поведение на разных frame rates.

## Обработка ошибок

- **ERR-001** — Использовать `check` и `checkf` только для внутренних инвариантов, после нарушения которых продолжение невозможно. Использовать `ensure` для восстанавливаемой ошибки разработки. Проверять сетевые, файловые и пользовательские данные обычными условиями без `check`.
- **ERR-002** — Не допускать побочных эффектов в выражении внутри `check` или `checkf`. Не помещать туда создание, присваивание, загрузку или регистрацию: в Shipping такой код может не выполниться. Выполнять обязательное действие отдельно, затем проверять результат.
- **ERR-003** — Учитывать, что `ensure` не останавливает выполнение. После неуспешного `ensure` переходить в безопасную ветку: выполнять `return`, отменять операцию или применять допустимый fallback. Не продолжать обращаться к невалидным данным.
- **ERR-004** — Не использовать `throw`, `try` и `catch` в gameplay runtime-модулях. Возвращать явный статус ошибки. Допускать исключения только внутри изолированного адаптера сторонней библиотеки с явно включённым `bEnableExceptions`; на границе преобразовывать исключение в обычный результат.

## Безопасность

- **SEC-001** — Не хранить API keys, private keys, backend credentials и другие секреты в клиентском коде, config или assets. Считать содержимое packaged Client полностью доступным игроку. Хранить секреты только на сервере или backend.
- **SEC-002** — Не записывать в logs, crash reports и analytics access tokens, auth headers, персональные данные и полное содержимое сохранений. Маскировать чувствительные поля до передачи в логирование.
- **SEC-003** — Считать недоверенными все данные из сети, backend, файлов пользователя, command line и mods. До изменения игрового состояния проверять тип, schema version, размер, диапазоны и допустимые идентификаторы; при ошибке отклонять данные без частичного применения.

## Multiplayer

- **NET-001** — Сервер авторитетно изменяет здоровье, урон, боеприпасы, инвентарь, валюту, cooldown, счёт, смерть, spawn и итоговое положение. Клиент передаёт только ввод или намерение. Разрешать клиентскую предикцию движения и визуальных эффектов, но проверять и исправлять результат на сервере.
- **NET-002** — В каждом Server RPC проверять владельца, права, текущее состояние, допустимость параметров и частоту вызовов. Отклонять невалидный запрос.
- **NET-003** — Передавать постоянное игровое состояние через replicated properties. Использовать RPC только для запросов и кратковременных событий.
- **NET-004** — Не вызывать Reliable RPC каждый Tick. Использовать Reliable только для редких событий, которые обязательно должны быть доставлены; частые данные передавать через replication или Unreliable RPC.
- **NET-005** — Вызывать Server RPC с клиента только на реплицируемом объекте, которым клиент владеет. Направлять взаимодействия с дверями, предметами и другими объектами мира через принадлежащий клиенту `PlayerController`, Pawn или компонент.
- **NET-006** — Не реплицировать клиенту скрытые данные, которые он не должен знать: невидимых противников, секретные цели, серверные проверки и состояние anti-cheat.
- **NET-007** — Тестировать multiplayer-функцию на отдельном сервере минимум с двумя клиентами, добавляя задержку и потерю пакетов. Не считать однопроцессный PIE достаточной проверкой.
- **NET-008** — Использовать в проекте только Mover. Не связывать игровых персонажей с `ACharacter` или `CharacterMovementComponent`; основывать их на `APawn` или Actor с `UMoverComponent`. Не принимать зависимости, требующие CMC. Осознанно принять experimental-статус Mover.
- **NET-009** — Фиксировать версии Unreal Engine и Mover. Выполнять обновление отдельной задачей только после сетевых тестов предикции, коррекции и rollback на выделенном сервере.
- **NET-010** — Хранить все параметры, влияющие на симуляцию Mover, включая режим, стойку, скорость, ускорение и модификаторы, в Sync State или Aux State Mover. Не читать в симуляции несинхронизированные изменяемые поля.
- **NET-011** — Хранить серверные правила матча в `GameMode`, общее реплицируемое состояние матча в `GameState`, а состояние игрока в `PlayerState`. Не хранить в `PlayerController` данные, необходимые другим клиентам.
- **NET-012** — Не полагаться на порядок получения реплицируемых свойств и RPC между разными Actors. В `OnRep` и RPC проверять зависимости и корректно ждать, если связанный Actor ещё не реплицирован.
- **NET-013** — Рассчитывать cooldown, respawn и таймер матча на сервере по времени окончания. Реплицировать клиенту timestamp окончания; оставшееся время вычислять на клиенте только для отображения. Не считать клиентское время авторитетным.
- **NET-014** — Определять на сервере случайные результаты, влияющие на gameplay: loot, критический урон, разброс и шанс срабатывания. Разрешать клиентский random только для визуальных эффектов. Для предикции использовать синхронизированный seed с проверкой результата сервером.
- **NET-015** — Выполнять покупку, crafting, trade и выдачу награды на сервере как атомарную операцию с уникальным ID запроса. Не допускать повторного списания или выдачи ресурсов при повторном запросе с тем же ID.

## Сохранения

- **SAVE-001** — Добавлять в каждый файл сохранения версию схемы. Явно мигрировать старые версии. Не загружать и не перезаписывать автоматически сохранение с неизвестной версией или повреждёнными данными.
- **SAVE-002** — Не сохранять указатели на `UObject` или Actor. Сохранять стабильные идентификаторы: ресурсы через `FPrimaryAssetId`, игровые сущности через постоянный `FGuid`. При загрузке заново разрешать ссылки и обрабатывать отсутствующие идентификаторы.
- **SAVE-003** — Записывать сохранение атомарно: сначала во временный файл, после успешной записи заменять основной. Хранить последнюю рабочую резервную копию. Не допускать уничтожения предыдущего сохранения при прерванной записи.
- **SAVE-004** — В multiplayer хранить прогресс, инвентарь, валюту и права доступа только на сервере или backend. Не считать клиентское сохранение источником истины для этих данных.

## Тестирование

- **TEST-001** — Перед merge успешно собирать `Editor`, `Client` и `Server` targets и запускать связанные автоматические тесты. Блокировать merge при любой ошибке.
- **TEST-002** — Выбирать минимально достаточный уровень теста: Low-Level Tests для изолированной C++-логики, Automation Spec для интеграции с системами Unreal Engine, `AFunctionalTest` для gameplay и карт, Gauntlet для packaged builds и многопроцессных сценариев.
- **TEST-003** — Делать каждый тест независимым от порядка запуска и исходного состояния Editor или игры. Создавать собственные данные, очищать изменённый мир и файлы, допускать параллельный и повторный запуск.
- **TEST-004** — Не использовать фиксированный `Sleep` или `Delay` для синхронизации теста. Ждать проверяемое условие с ограниченным timeout и завершать тест ошибкой с диагностикой при превышении времени.
- **TEST-005** — Добавлять к каждому исправлению дефекта регрессионный тест, который воспроизводит дефект без исправления и проходит после него. Если автоматизация технически невозможна, фиксировать причину и детерминированный ручной сценарий проверки.
- **TEST-006** — Не считать тест в Editor заменой теста packaged build. Перед релизом запускать критические gameplay-сценарии на packaged `Client` и `Server` для каждой целевой платформы.
- **TEST-007** — Запускать Data Validation всего проекта в CI и блокировать сборку при невалидных ресурсах. Реализовывать собственные валидаторы для обязательных проектных ограничений ресурсов.
- **TEST-008** — Помечать как Smoke только тесты длительностью до одной секунды и запускать их при каждом изменении. Запускать полные Functional, Content Stress и Gauntlet тесты отдельным обязательным CI-этапом.
- **TEST-009** — Хранить тестовые сохранения каждой поддерживаемой версии схемы. Проверять миграцию, повреждённые и обрезанные данные, прерывание записи и восстановление из резервной копии.
- **TEST-010** — Сохранять машинный отчёт и диагностические артефакты каждого CI-запуска. Не скрывать нестабильный тест автоматическим повтором: считать flaky-тест дефектом до устранения причины.

## Производительность

- **PERF-001** — Оптимизировать только измеренное узкое место. Сохранять результаты Unreal Insights или `stat unit` до и после изменения.

Обсуждение новых правил производительности отложено.
