# Feature workflow

Use Feature for exactly one eligible slice of one Roadmap feature. Both `feature_id` and `slice_id` are mandatory. A slice is the smallest gated delivery unit that produces one observable, runnable scenario; horizontal infrastructure work is allowed only as a bounded enabling slice with an explicit consumer.

1. Rehash and normalize current sources, compare them with the pinned baseline through `source-diff`, then verify the feature and slice prerequisites through the canonical graph's `feature_eligible` and `slice_eligible` predicates.
2. Load the current full-project `ArchitectureModel`, `ModuleCatalog`, and `SliceBacklog`. Research only what the slice needs, but review every affected module, dependency, runtime flow, and non-functional constraint. Produce one immutable `slice-plan/1.0.0` tied to the slice scenario and acceptance criteria.
3. Route systemic architecture changes through independent architecture review and its human gate. Publish one `architecture-delta/1.0.0` plus proposed complete revisions of the ArchitectureModel and ModuleCatalog; never patch the canonical architecture implicitly.
4. Obtain the slice-plan gate before preparing or mutating a worktree.
5. Before writing code, read [engineering-rules.md](engineering-rules.md), call `engineering-status` without a baseline, and publish one immutable `engineering-rule-applicability/1.1.0` contract bound to the feature, slice, plan, catalog hashes, clean current Git revision, and applicable rule IDs. Stop on a dirty worktree or stale project policy.
6. Implement only the approved slice tasks and touched modules. Immediately run the mandatory playable `slice-smoke-result/1.0.0` scenario after implementation. A failed smoke returns to implementation; it cannot be deferred or waived as optional coverage.
7. Require independent code review after the smoke passes. Produce a risk-based plan only for additional coverage; the declared human test gate may defer or waive that additional coverage, never the slice smoke.
8. After the final implementation and test diff, call `engineering-status` with the applicability baseline and require an independent `engineering-compliance/1.1.0` contract bound to the feature, slice, applicability, current HEAD/diff hash, every applicable rule's evidence, violations, and verdict.
9. Verify `slice_complete` and `architecture_consistent`, then publish one `slice-verdict/1.0.0`. Obtain slice acceptance, merge locally, atomically publish the slice status, traceability links, architecture revision when applicable, module maturity, and feature progress, commit those exact records, optionally remote-sync, then clean up the worktree.
10. A feature becomes complete only when every required child slice is verified and `feature_complete` passes. Never infer feature completion from one successful slice.

Never silently expand scope, implement a second slice, split work into unplayable horizontal milestones, rewrite source requirements, waive a failing smoke or engineering-rule violation, or merge without its declared gate. Filesystem, atomic project-record publication, local Git, guarded local worktree cleanup, canonical Build/Test, and allowlisted Unreal MCP actions are available. Git LFS mutation, push, and Network/Research remain optional and fail-closed; their absence does not block a local slice, but selecting one without an executor does. The first real pilot must follow [forward-test.md](forward-test.md) and stay text-only.
